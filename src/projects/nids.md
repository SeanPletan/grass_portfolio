# 0. Introduction
I created an intrusion detection system that can be deployed on any network. There are many pre-compiled datasets for the explicit purpose of network intrusion detection. However, this was a semester-long university project, and one of the constraints was end-to-end data collection and processing. A machine learning model was trained on that data, and any intercepted network packet can be evaluated for the probability of being anomalous. 

The blog is divided into 5 parts: Network Setup, Traffic Simulation and Data Collection, AI Model Development,  Issues and Limitations, & Conclusion

# 1. Network Setup
A virtual network was created on one physical machine. Within this network were several virtual devices:

* pfSense Router: acting as a DHCP server and gateway for the network. It also acts as a DNS server for the fictitious getpwned.gg domain, but otherwise does not participate in attacks or meaningfully contribute to data collection.

* Linux Mint Victim: host representing a legitimate user, used as a victim for certain attacks.

* Ubuntu Server: host representing (and hosting) a web server, used as a victim for certain attacks.

* Ubuntu Victim: host representing another legitimate user.

* Kali Linux Attacker: host representing an attacker, used to attack other hosts, as well as pretending to be a legitimate user.

* 4x Arch Linux Attacker: hosts representing a botnet-like cluster controlled by the attacker (Kali Linux).

* Kubuntu Gamemaster: host coordinating attacks, and collecting all data; connected to all devices on the 192.168.56.0/24 subnet.

Within the virtualized world, there are 2 subnets, 192.168.56.0/24 and 192.168.10.0/24. The pfSense router acts as the default gateway for the .10.0/24 subnet, which only has 1 device on it: the Ubuntu server. 
The gamemaster is connected to all devices via a separate virtual network interface, except the router, to control the simulation. These are the red lines. This was done to avoid poisoning the ML training data with simulation control data. On the right, you'll see the .56.0/24 subnet. This is in front of the router and simulates both outside attacks on a firewalled network, and attacks within a network. You'll now probably notice the black lines. These represent devices connected to one another within the simulation at one point in time or another.

# 2. Traffic Simulation and Data Collection

8 different types of attacks were simulated: SYN floods, UDP floods, HTTP floods, TCP SYN scanning, active version fingerprinting, botnet SYN floods, botnet UDP floods, and botnet HTTP floods. Indeed, not many different archetypes of attacks. Only DDoS, DoS, and reconnaissance. Attack traffic was marked by a UDP packet sent by the attacker on destination port 31337 to make programmatically identifying attacks easier. All data was captured by tshark and sent to the gamemaster as PCAPng files upon completion. 

The software used to perform attacks were hping3, siege, and nmap only.

Normal traffic was performed manually. This was because automated normal traffic is difficult to generate due to the devices' headless nature, e.g. no web browser could be run on it outside of perhaps a docker container. 

# 3. AI Model Development
Model development began with deciding between supervised and unsupervised models. Supervised models are easier to train assuming your data has the classes labeled and at the time mine did not. The original hope was to use an autoencoder to be trained on a large amount of normal traffic, but generating that amount of normal traffic turned out to be difficult as mentioned in the issues and limitations. I ended up with two models, Random Forest(supervised) and Isolation Forest(unsupervised). Both were trained on flow-rate traffic generated by aggregating the packet-level traffic. Both models were experiencing high classification results that were basically 100% accuracy, recall, and F1. Due to lack of confidence in the labels, I initially decided to stick with the Isolation Forest model.

However, at the undergraduate research symposium, model feedback led to a complete overhaul of the pipeline. I created labels for the data, removed the flow feature set, and removed all time-related features in order to decrease data leakage and the risk of overfitting. 

So, in order to create the labeled data, I parsed through the generated .pcapng files, which included packets denoting where attacks 'begin' or 'end' (within the payload). I did this by generating a json file from the pcapng file (to make it parseable by a python program, and because pyshark was simply not versatile enough). The python program appended an 'attack' column on the .csv file that denoted if an attack happened or not.

Then, in order to improve data balance (the data frame that I was using had a 99.99:0.01 ratio of attack to non-attack), normal data was concatenated onto the training data after a sampling. This normal data had an additional column called 'attack' that was set only to 0. As a result, the ratio of attack : normal traffic was 50.26 : 49.74.


After this, I had to clean the data. Some records had 20 columns, instead of 15, some sets of features were NaN for different protocols, and some features had to be combined. An array was made with the indices of records with incorrect number of columns, and those indices were dropped from both the label set and data set. Then, I combined the udp.srcport/dstport with tcp.srcpor/dstport into just srcport and filled all records with NaN's with 0's. Additionally, of the now 11 features, 5 of them were categorical features. These needed to be encoded, so I chose a simple label encoder.

In the final product, both a random forest classifier and a decision tree classifier were trained. Because random forest is an ensemble method, it is much more powerful, and the risk of overfitting the data is greatly increased. This is most noticeable in Table 1. Naturally, decision trees were the next step forward in reducing overfitting. Both models had an f1-score of above 99.9 with the full feature set. So, feature selection occured. Features were dropped, sorted by feature importance (for example, when the decision tree classifier was trained on 4 features, those 4 features were udp.length, ip.proto, tcp.flags.syn, and srcport).

# 4. Issues and Limitations
The attacks were limited in that there was no way to randomize source addresses for some classes of attacks, namely a stealthy HTTP flood. This resulted in simplistic attacks with little-to-no variation, causing all machine learning models to overfit. One possible solution is "simply" filling the entire subnet with hosts. While this is feasible on a /24 subnet with relatively few compute resources (e.g. 8 virtual machines running 32 containers bound to their own interfaces), this creates additional logistical issues and cognitive overhead in that such a system would necessarily have to be provisioned through Infrastructure-as-Code (maybe Vagrant or Ansible).

For normal traffic laced with attacks, all attacks were run sequentially; at no point were the attacks allowed to run at the same time or otherwise overlap. This further exacerbated overfitting in the ML models.

Additionally, in the final product, flow data was removed. Had there been more advanced types of attacks, this aggregated data could have been used to increase the F1 score, potentially without increasing the risk of overfitting. Indeed, the attacks used were very single-faceted and not very advanced. Here is a list of potential types of attacks that could advance model training:
* Brute Force login attempts
* SQL Injection
* Cross-Site Scripting (XSS)
* Man-In-The-Middle Attacks
* Reverse Shell
* Remote Code Execution

… and here are 2 pieces of software that could be used to inject these attacks into the virtual network: 
* Metasploit Framework
* Burp Suite

# 5. Conclusion
The final product was an intrusion detection system capable of evaluating network traffic for anomalous behavior using a decision tree classifier. By creating a fully virtualized network, simulating both normal and attack traffic, and developing a machine learning pipeline, I demonstrated a complete end-to-end workflow from data collection to model deployment. While the attacks used were only DDoS and reconnaissance, the methodology lays the foundation for incorporating more advanced attack types in the future.
