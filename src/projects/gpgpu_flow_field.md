subheading:A .glltf model of a ship made out of hundreds of thousands of particles, computed with the GPU

summary:This scene demonstrates particle shading, GPGPU, and flow fields by rendering a 3D model as hundreds of thousands of animated particles whose size, color, position, and lifespan are computed on the GPU. Particle data is stored in frame buffer objects (FBOs), which are updated each frame using a ping-pong technique so the GPU can efficiently process all particles in parallel. Movement is driven by a time-varying 4D simplex noise based flow field.

The title of this section best explains what it is in one sentence. This scene uses several techniques: particle shading, general purpose computing on graphics processing units (or GPGPU), and flow fields. We'll go into particle shading first. First, as a proof of concept, I created a sphere, and then set the material to ShaderMaterial(). I then displayed each vertex as a circle (point) using the Points() method and vertex/fragment shaders. I also sent the color of the model (geometry, for now) as a varying to the fragment shader, and handled particle size by calculating its size proportional to window size. Basic stuff. Next, I handled the GPGPU.

GPGPU refers to the use of GPUs to accelerate non-graphical computations. Modern GPUs are massively parallel devices, consisting of hundreds or thousands of smaller processing units (CUDA cores or equivalent stream processors) that can perform computations simultaneously. GPGPU takes advantage of this parallel architecture by distributing computational tasks across many threads, allowing for high throughput in data-parallel applications. Unlike CPUs, which are optimized for serial processing with a few powerful cores, GPUs excel at tasks that can be decomposed into many independent operations. This makes them particularly suited for problems in scientific computing, machine learning, image processing, and simulations, where operations like matrix multiplications, vectorized operations, and spatial computations can be processed in parallel. In this program, there are 250,826 vertices (and, in turn, particles), and for each, there is a series of algorithms to determine color, size, position, and lifespan.

However, first, I had to get the particle position and lifespan into a data format that the GPUComputationRenderer() Three.js class could understand. That involves creating 2 frame buffer objects, and mapping each particle's x,y,z, and time attributes to a pixel on the FBO texture where it has r,g,b, and a attributes. On each frame, the FBO is updated with the previous frame's particle positions. The GPUComputationRenderer() applies a series of algorithms to the FBO to achieve the desired performance. However, FBOs cannot be read from and written to simultaneously, so after each frame, I choose the other FBO (out of 2) to modify, keeping one FBO unmodified.

As for the algorithms to compute color, size, position, and lifespan, it's a bit more straightforward. The color for each particle is derived from the color attribute of the GLTF model's geometry. The size is a uniform, uSize, defined in the ShaderMaterial declaration (which is added to lil-gui's tweaks). The size is randomized by multiplying it by a random value from 0 to 1, and the result is sent to the vertex shader as an attribute, aSize. in the vertex shader, there is an additional functionality defined: particle lifespan. I wanted to control the size such that they grow slowly from inception, stay at their largest size for the same amount of time, and then even more slowly, shrink down to a size of 0. The output of that function is saved in a variable called size (in the vertex shader). The final point size is calculated by multiplying uSize, aSize, size, and the screen height (to normalize it to the viewer's window size) together. Good. That's done. Next up is position.

At the highest conceptual level, you can think of it as a 4 dimensional Simplex Noise function (3 dimensions with the 4th dimension representing time. In other words, the noise function changes with time) overlaid onto the scene. Where the noise has a value of 1, the flow field (which is also overlaid onto the scene) is applied to the particle at that point. I will not cover how simplex noise works, but if you aren't familiar with it, you can think of it as a pseudo-random value applied over 1 to 4 dimensions. Noise. Like TV static. The flow field is where all of the movement in the particles originate from. The flow field is a field of vec3's, where the x, y, and z portions are outputs of the simplexNoise4D(particlePosition * uFlowFieldFrequency + offset, time) function. The offset is necessary to avoid diagonal movements and to keep it random. You might recognize the uFlowFieldFrequency, as it is a tweak available to the end user in the top right corner of the screen. I'll go over that later. Time, of course, is the 4th dimension in this function. It is necessary to continually change the flow field.

Right. That's the general overview of the theory, and so I only have a couple more things to explain. The first being the effects of changing the tweaks in the top right corner. clearcolor, of course, is the background color. uSize is one of the 4 inputs to the final equation to determine particle size. uFlowFieldInfluence affects how much of the simplex noise function (overlaid onto the scene) is a 1 (1 meaning the flow field affects the particle). So, when uFlowFieldInfluence is 1, a flow field is applied to every single particle. While a 0 means that the flow field is not applied to any particle. uFlowFieldStrength is pretty simple. It's just a scalar multiplied to the particle position vector in one of the final steps. uFlowFieldFrequency scales the amount of how much the particle's position influences the flow field vector's calculation. So, if uFlowFieldFrequency is 0, the particle's position is not an input into the flow field's calculation. The flow field remains constant. However for values above 1, it increases the amount of influence the particle's position has in the calculation of the next frame.
